# Shuriva UI Guidelines

## 1. 目标

保证 Shuriva 所有页面拥有统一的设计语言、
交互规则和前端工程结构。

避免：

- AI 生成的模板化界面
- 重复开发基础组件
- 页面风格不一致
- 复杂组件混入页面代码
- UI 与业务逻辑耦合
- 操作状态不明确
- 用户不知道下一步应该做什么

## 2. 技术栈

当前技术方向：

- React 19
- React Compiler
- TypeScript
- Vite 8
- Tailwind CSS 4
- shadcn/ui
- Base UI
- pnpm
- Oxlint

主应用采用 SPA / CSR。

具体依赖版本以 package.json 和锁文件为准。

不得随意升级主要依赖。

## 3. 视觉设计原则

整体风格：

- 简洁
- 专业
- 克制
- 高信息密度
- 强调数据可读性
- 具有产品辨识度

品牌视觉：

- 采用 Gemini-inspired 蓝紫色专业 SaaS 风格。
- 品牌主色使用统一 Design Tokens。
- 渐变仅用于品牌标识和 AI 相关区域。
- 数据展示区域保持中性、清晰。

设计要求：

- 使用统一 Design Tokens。
- 统一字号、间距和圆角。
- 统一按钮和输入框。
- 统一图标体系。
- 避免无意义的大面积卡片。
- 避免过度留白。
- 避免大面积渐变和发光效果。
- 不使用夸张装饰制造 AI 感。

优先使用现有设计规范。

## 4. 组件体系

基础组件：

shadcn/ui + Base UI。

业务组件由 Shuriva 自己维护。

禁止：

- 混用 Ant Design、MUI 等完整 UI 库。
- 重复实现已有基础组件。
- 在页面内堆积复杂业务逻辑。
- 随意修改全局组件视觉规范。

新增组件前先检查已有实现。

组件设计应遵循明确的职责边界：

- Page 负责页面组合。
- Feature 负责业务功能组织。
- Component 负责 UI 展示与交互。
- Hook 负责具有共同状态和行为的 React 逻辑。
- Service 负责外部数据访问和副作用。
- Schema 负责数据结构与配置校验。

不要为了减少文件行数而机械拆分组件。

不要为了复用而引入不必要的抽象。

## 5. 页面架构

核心页面：

- 首页
- 我的工作台
- 工作台使用页
- AI 创建与修改页
- 数据源管理
- 设置与权限管理

### 5.1 工作台使用模式

这是产品最重要的页面。

要求：

- 工作台占据主要空间。
- 显示指标、筛选、表格、详情和图表。
- AI 编辑面板默认关闭。
- 用户不需要与 AI 对话即可完成日常操作。
- 数据源状态清晰。
- 不同模块的数据来源明确。

### 5.2 AI 创建与修改模式

采用 AI 对话面板 + 工作台预览。

要求：

- 对话与预览职责分离。
- 新建状态与编辑已有工作台状态明确区分。
- 新建状态不展示虚构的业务数据、指标或已生成模块。
- AI 生成后才展示工作台结构。
- 修改先进入草稿。
- 用户可以预览变化。
- 保存后更新正式版本。
- 放弃修改不影响已保存版本。
- 修改失败保留上一个可用版本。
- AI 面板和工作台预览支持合理的宽度调整。
- AI 对话和预览的布局应符合当前产品设计决策。

### 5.3 首页

新用户：

突出创建工作台和示例体验。

老用户：

突出最近使用的工作台。

不要让首页长期成为空白聊天页面。

## 6. 动态 UI Renderer

AI 只能生成受控 UI Schema。

允许的组件由项目注册表决定，例如：

- Table
- MetricCard
- Filter
- Chart
- DetailPanel

所有 Schema 必须经过：

1. 类型校验
2. Schema 校验
3. 属性校验
4. 数据绑定校验
5. 权限校验

禁止：

- 任意 HTML 执行
- 任意 JavaScript 执行
- 任意 React 代码执行
- AI 自由指定全局 CSS
- 未经验证直接渲染 AI 输出

## 7. 多数据源界面

- 工作台允许引用多个数据源。
- 支持数据库和文件数据源。
- 数据源包括数据库连接、CSV、Excel、JSON 等受支持类型。
- 每个 Query 必须指定数据源。
- 每个组件必须指定 Query。
- 不同数据源状态独立。
- 一个数据源失败不应使其他独立模块全部失效。
- 数据来源应可追溯。
- 创建工作台时优先展示用户已经添加的数据源。
- 添加数据源入口应始终容易找到。
- 数据源列表应支持搜索、分类和多选。
- 数据库新增和文件上传使用各自合理的配置流程。
- 已选择的数据源不应造成创建页面布局拥挤。
- 数据源选择与添加应与数据源管理模块使用统一的数据模型。

不能因为用户切换侧栏数据源，
就改变已保存工作台的查询绑定。

## 8. 状态设计

重要组件必须考虑：

- Loading
- Empty
- Error
- Success
- Disabled
- Offline
- Permission Denied

不得只实现正常状态。

状态设计应明确：

- 当前发生了什么。
- 为什么发生。
- 用户接下来可以做什么。
- 是否可以重试或恢复。

### 8.1 主操作与交互引导

**核心原则：主操作优先保持可用，前置条件通过交互引导完成。**

Shuriva 面向需要快速完成业务任务的用户，不能让用户因为缺少某项配置而不知道为什么无法继续。

#### 主操作按钮

对于创建、生成、保存、连接、提交等主要操作：

- 不要仅因为用户尚未填写表单、选择数据源或完成配置，就将主操作按钮设置为灰色禁用状态。
- 在存在明确引导路径时，主操作按钮应保持正常的品牌主色和可点击状态。
- 用户点击后，再检查当前操作的前置条件。
- 如果条件不满足，明确告诉用户缺少什么，以及如何完成。
- 条件满足后，直接执行操作，不增加不必要的确认步骤。

#### 前置条件反馈

当用户点击主操作按钮时：

1. 检查必要输入。
2. 判断缺失的前置条件。
3. 提供明确、友好的提示。
4. 将用户引导到对应的解决位置。
5. 用户完成操作后，允许重新执行主操作。

例如：

**没有填写业务需求**

- 提示用户先描述想创建的工作台。
- 将焦点定位到需求输入框。
- 在输入区域附近展示清晰的提示。
- 不要只显示一个短暂 Toast。

**没有选择数据源**

- 提示用户需要选择已有数据源或添加新数据源。
- 提供直接打开数据源选择界面的操作。
- 不要让用户自己寻找下一步入口。

**数据源连接失败**

- 明确展示失败原因。
- 提供重新连接或修改配置入口。
- 不要将连接失败显示成正常可用状态。

**多个前置条件同时缺失**

- 优先处理当前最重要、最先需要解决的条件。
- 不要一次显示大量错误提示。
- 每完成一个步骤，再引导用户解决下一个条件。

#### 反馈方式

根据问题类型选择合适的反馈方式：

| 场景           | 推荐方式                  |
| -------------- | ------------------------- |
| 必填内容缺失   | 输入框附近的行内提示      |
| 数据源未选择   | 引导提示 + 打开数据源选择 |
| 配置不正确     | 字段级错误信息            |
| 网络或服务异常 | 错误提示 + 重试入口       |
| 操作成功       | Toast 或明确的状态反馈    |
| 长时间执行     | Loading + 进度或阶段说明  |
| 权限不足       | 说明原因及可执行的下一步  |

不要只依赖 Toast 表达需要用户处理的重要问题。

连接测试等页面内操作，应把等待、成功和失败反馈放在发起操作的按钮旁或正下方，与对应模型或配置项明确关联。不要用右上角全局 Toast 承担这类操作的反馈，用户的注意力仍在刚点击的位置。

长表单还需检查结果是否实际处于用户视野内。保留明确的完成状态，并避免用户已经滚动离开后又被自动拉回。

#### 允许使用 Disabled 的情况

Disabled 不是禁止使用的状态。

以下情况可以使用：

- 操作正在执行，防止重复提交。
- 用户没有权限执行该操作。
- 当前操作在业务上确实不可执行。
- 系统资源或流程状态不允许执行，且没有合理的即时解决路径。
- 防止重复触发不可逆操作。

即使使用 Disabled，也应在适当位置解释原因。

不要将 Disabled 当作处理表单校验和前置条件缺失的默认方案。

#### 交互设计禁止事项

- 不要让主要按钮在用户首次进入页面时就呈现为不可用状态。
- 不要只通过灰色按钮让用户猜测缺少什么。
- 不要在用户点击后只返回无意义的「操作失败」。
- 不要要求用户自行寻找缺失的配置入口。
- 不要在一个操作中同时展示大量互不相关的错误。
- 不要使用成功 Toast 掩盖实际失败。
- 不要在没有必要时增加多层确认弹窗。

## 9. 响应式

优先支持桌面端。

同时保证：

- 常见笔记本宽度可用
- 导航可收起
- 表格支持横向滚动或合理适配
- 详情抽屉在窄屏下有合理表现
- 创建模式在窄屏下可以切换对话和预览
- 左右可调节布局在窄屏下提供合理的替代方式
- 输入框、按钮和弹窗不发生布局溢出

## 10. 开发流程

1. 检查现有页面和组件。
2. 确认设计规范。
3. 确认页面结构。
4. 复用基础组件。
5. 实现业务组件。
6. 明确状态所有权。
7. 实现交互状态。
8. 实现前置条件检查与用户引导。
9. 实现异常状态。
10. 检查响应式。
11. 使用浏览器验证。

开发过程中应检查：

- 主操作按钮是否存在不必要的 Disabled 状态。
- 前置条件缺失时是否提供明确反馈。
- 是否能够直接引导用户解决问题。
- 用户完成引导后能否继续原操作。
- 是否存在重复提示或无意义确认步骤。

## 11. 验收标准

- 视觉风格统一。
- 组件复用合理。
- 没有无效按钮。
- 主要操作按钮不会仅因普通前置条件缺失而灰色禁用。
- 前置条件缺失时有明确、友好的反馈。
- 提示能够引导用户完成下一步。
- 重要错误具有对应的恢复方式。
- 所有交互可操作。
- 没有明显布局溢出。
- 加载和错误状态完整。
- 不破坏已有页面。
- AI 修改预览和正式工作台使用相同 Renderer。
- 新建工作台和编辑已有工作台的状态正确区分。
- Mock 数据和真实业务能力明确区分。
- 权限和数据安全不能仅依靠前端 UI 隐藏保证。
