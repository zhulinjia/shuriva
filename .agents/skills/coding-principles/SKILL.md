# 编码原则

目标：在实际约束下交付符合需求、可靠、易理解且可持续修改的代码。以下原则是决策依据，不是机械执行的检查清单；具体做法随任务、风险、技术和项目而变。

## 稳定原则

1. **解决真实问题**：以用户目标、可观察的正确行为和约束定义成功。区分事实与假设；在授权范围内完成任务，保留与任务无关的改动和行为。

2. **保证行为可靠**：明确接口及状态的含义，考虑与改动相关的边界、失败和恢复。依据影响与发生可能性处理风险，包括数据、安全、并发和外部副作用；不掩盖错误或将未知结果当作成功。

3. **让代码易于理解和修改**：职责、命名、数据流、契约和依赖应反映真实语义；按职责、共同变化的原因和依赖关系组织代码，在函数、文件和模块三个层面审视边界，使紧密相关的内容保持内聚，减少独立职责之间的相互影响。对于组件化框架，还应检查组件职责、状态归属和跨组件协作关系。权衡拆分带来的追踪和协作成本，降低理解和修改成本。优先使用项目已建立且适合问题的做法。

4. **复杂度与需要相称**：在满足当前要求及必要风险控制的前提下，选择足够简单的方案。抽象、依赖、配置或兼容机制要有现实依据；局部改动不应引入无关重构，也不能以改动少为由忽略正确性。

5. **用证据建立信心**：按变更和风险选择验证，检查关键行为和真实回归；区分静态检查、自动测试和实际运行的证据范围。报告结果及未验证的限制，不将假设表述为事实。

## 应用于编码任务

- 若本 Skill 的[经验索引](references/learned-rules.md)已存在，先读简短索引，按条目的触发条件和适用范围选读；没有经验文件时正常工作，不创建空条目。只将适用且已验证的经验用作决策依据，待验证项用于提示需要核实的问题。

- 明确预期行为、边界和完成标准；查看适用项目约定、相关实现与调用方，判断现有行为和风险。关键决策无法合理推断时再澄清，普通细节作合理假设并继续。

- 按下述设计方案与模式选择流程主动比较方案。涉及结构调整时，按职责、变化原因和依赖关系同时核对函数、文件与模块边界，不能以函数已拆分或入口已简化代替这项判断。原则冲突时，以明确需求、项目约束和实际风险权衡：例如小改动若会破坏共享契约，应选择能维护契约的必要改动。

- **React 与组件化项目的专项边界检查**：当 Page、Renderer 或大型 Component 同时承担页面组合、多个业务模块状态、数据转换、副作用和不同业务类型的条件渲染时，必须进一步检查组件、文件与 Feature 模块边界。明确组件职责、状态所有者、数据流、跨模块依赖和副作用归属。相关经验见 `READ-001`。不能仅通过提取 JSX、拆分函数或减少单个文件行数判断结构已经改善。没有独立职责或变化原因的小组件不必机械拆分。

- 实现时沿用适用的现有结构，清晰表达输入、输出、状态及错误；在相关边界做必要校验。验证与改动相称，遵守项目要求；交付时说明结果、验证及实际限制。

### 主动选择设计方案与模式

实现、修复或重构时，主动识别设计问题并选择合适方案，不等待用户点名模式。判断限定在本次目标和相关影响范围内；简单任务可直接沿用适用的现有做法，无需为了走流程制造候选方案、遍历模式清单或扩大重构。

**识别问题和变化点 → 比较直接实现与候选模式 → 说明取舍 → 验证结构与行为。**

1. **识别问题和变化点**：结合相关代码与调用方，明确当前要改善的问题、会独立变化的职责或依赖，以及必须保留的行为和状态约束。区分已有事实与推测，不以分支数量、文件长度或模式名称代替问题分析。

2. **比较可行方案**：以足够简单的直接实现或适用的项目既有做法为基线；有现实问题时，再考虑能改善该问题的设计模式或其它组织方式。只比较与当前场景相关的候选，不为假想扩展预建框架。

3. **说明取舍并选择**：比较正确性、理解与修改成本、影响范围，以及新增间接层、类型、状态和协作成本。采用模式时，应能说明它如何改善具体问题，以及收益为何值得付出这些成本；收益不清或直接实现更合适时，保留直接实现。选择满足需要的最小结构，不为模式名称增加类、工厂、注册机制或依赖。

4. **验证结构与行为**：检查目标职责、依赖和修改影响是否得到改善，同时按风险验证相关行为、失败及副作用边界；不能只用测试通过证明设计合理。若方案增加追踪负担且没有对应收益，应收缩或放弃该抽象。关键取舍和验证限制按下节要求保留依据。

## 决策与交付的可复查性

按任务影响保留足够依据，使他人能沿着目标和约束理解改动、核对结论；沿用项目已有的决策文档、差异、检查输出或交付说明，不为每次小改动另建记录体系。

- 对影响行为、职责边界、依赖或复杂度的关键选择，说明对应的问题、事实与假设、可行方案的取舍及选择理由。只记录会改变判断的依据，不机械穷举方案或补写未经考虑的比较。

- 交付前对照完成标准核对实际差异、相关调用方及关键边界。结构目标与行为验证分别核对；发现未完成事项或相邻问题时，说明是否影响当前目标及其依据，不将其静默当作已解决。

- 重要验证结论应能定位到实际检查方式、结果及相关环境；区分类型检查、模拟用例、真实运行和人工结构复核的证据范围，明确未验证部分。失败或未执行的检查不能合并成“全部通过”。

本 Skill 支持按证据交付，不保证加载后就会正确执行。若评价某次工作是否达到某个等级，先明确采用的定义和范围，再依据实际改动与证据判断；规范条目数量、设计模式名称或一次测试成功不能单独证明设计合理。

## 从原则推导开发规范

当用户要求制定或改进规范时，先了解目标项目、语言、运行环境、团队现状和已有规则；无法确认的信息标为假设，不将缺失信息编造成项目事实。再按以下逻辑推导，每条规则都应服务于可识别的质量目标：

**原则 → 具体场景和风险 → 可执行规则 → 验证方式 → 适用范围或例外**。

- 规则要能指导选择或判断，说明何时适用及如何检查；区分必须遵守的约束、推荐做法和需要结合情境判断的建议。不要把尚无授权的新规则写成已有项目要求。
- 为规范选择与项目规模及风险相称的严格度；避免把语言、框架或工具的偏好当成跨项目真理，也避免用覆盖率数字、函数长度等单一指标代替质量判断。
- 对规则间冲突说明权衡依据；当例外成立时，说明需要保留的质量目标及验证证据。若缺少关键信息，先交付带明确假设的可用草案，并指出影响决策的待确认事项。
- 例如：由「保证行为可靠」针对支付接口可能重复提交的风险，可推导「对结果未知的支付请求，先查询结果或使用服务端支持的幂等机制，再决定是否重试」；通过模拟超时后服务端已处理的场景验证。该规则仅适用于有此类副作用和能力的场景，不普遍要求所有请求使用幂等键。

## 自我迭代与扩展

本 Skill 可在使用中维护自己的派生规则与经验；五项原则保持稳定。用户纠正、可复现问题、验证得出的有效改进，或旧规则被反例推翻时，主动判断是否需要更新。没有会改变后续决策的新证据时，无需更新。

触发迭代时，读取[迭代协议](references/evolution.md)：先核实证据、搜索已有规则，再优先修订或合并；需要新能力时按主题扩展。将可复用经验写入本 Skill 内的持久文件，使后续相关任务能读取、应用并重新检验。

普通经验维护可在当前授权和文件权限内直接完成，并在交付时简述变更；修改稳定原则需用户明确要求或认可。经验维护不授权修改其他 Skill、项目指令或外部系统，也不授权安装依赖。无法写入时，交付具体待应用改动，说明尚未保存。

系统、开发者和用户的有效指令优先于本 Skill，适用的项目规则在其范围内生效；本 Skill 不扩大授权。与领域专项 Skill 配合时，按任务取用，避免重复或冲突。
