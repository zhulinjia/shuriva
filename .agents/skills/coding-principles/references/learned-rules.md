## READ-001：按语义职责组织代码边界

**最近修订：2026-11-06。对应原则：**让代码易于理解和修改、复杂度与需要相称；重构验证同时遵循行为可靠与证据原则。

**范围与风险：**入口或回调同时处理多个操作意图、配置、外部调用、结果判定或恢复等独立职责，或文件、模块容纳了可独立变化的职责，导致读者需要同时记住多个上下文时适用；依赖加载没有明确边界却引入额外异步层时，也应检查这种阅读负担。统一注册、表驱动或减少重复本身不能证明代码容易理解。这是按语义边界审视代码的判断方法，不要求所有项目采用相同结构。

### 可执行规则

- 出现上述混合职责并遮蔽主流程时，先识别操作意图和各语义阶段。名称、参数及内部类型应反映实际支持的操作；不同操作各自表达流程，共同入口只承担必要的校验、分发和公共错误边界。逐个分支检查是否仍嵌入完整操作流程；将 if 换成 switch 或处理器表不能单独证明职责已经分开。

- 当同一个稳定判别项（如方法名）选择相互独立的操作，且各操作共享入口约束时，比较显式分支与函数策略表。若每项操作能独立承担自己的参数校验、流程和结果判定，策略表可使入口收敛为选择与调用；优先使用满足需要的普通函数映射，不为模式名称增加策略类、工厂或动态注册框架。没有统一的分支数量门槛，也不以策略表替换同一流程内的合法性、顺序或失败判断。

- 策略的公共调用形状应服务于真实操作边界；外部原始输入可统一接收，内部仍按各自权威 Schema 收窄，不能为统一签名扩大业务契约或增加大量标志参数。分发整理须保留未知操作拒绝、公共连接或权限检查、异常边界及副作用顺序；选择必须精确命中已登记的操作，避免普通对象的原型成员被误当成处理器。

- 依赖集合已知、且没有加载时机或宿主隔离依据时，优先静态导入，使依赖关系直接可见；不要仅为取得固定依赖，增加返回动态 import 的异步包装和调用链。动态加载需要对应实际边界，例如模块初始化会注册当前宿主以外的监听器；明确这种依据后再选用，不能把本条理解为禁止动态导入。

- 流程层优先表达步骤、顺序和失败边界，将命令参数、文件格式等实现细节放在有明确职责的操作中。按读者需要的语义层次组织，不要求每个步骤都提取函数，也不为此预建通用框架。

- 表达式同时完成对象选择、路径生成、状态读取等不同阶段且增加理解负担时，用有意义的中间变量或函数名显式表达。单一字段映射、公共字段展开或直接条件分支仍可内联。

- 将“什么算失败”“什么情况下结果未知”等关键判断明确表达；仅在命名能揭示独立语义时提取函数，避免把判断藏在过密的条件表达式或对象展开中。

- 从入口、函数继续检查所在文件与模块的职责、变化原因和依赖：不同职责已拆成函数后，仍要判断它们是否需要共同维护；可独立理解和修改、缺少共同约束的职责，应比较分离后的修改影响与依赖成本。只搬走长回调、缩短文件、拆出大量含糊的小函数或增加文件数，都不能作为可读性改善的依据。比较读者需要同时记住的上下文及跨边界追踪成本；结构目标需要单独核对，类型检查与行为测试通过不能证明可读性改善。

- 拆分时保留事务、锁、资源生命周期、异常捕获及结果语义的边界。涉及外部副作用时，按风险对照产物、操作顺序、失败恢复和对外错误，不能只验证成功路径或类型检查。若要求行为不变，区分结构整理与失败策略、输入接受范围等行为修改；明确保留的限制，不把类型断言当成运行时校验，也不把尽力恢复描述为保证恢复。

### 来源与验证摘要

后续安装器案例中，同一函数混合安装与卸载、参数解析、文件与注册表操作、备份和恢复；用户要求按上述方向整理且保持功能不变。整理后分别表达两种流程，收紧内部操作类型，展开多阶段表达式，并隔离平台操作。相同的 12 个隔离用例在重构前后均通过，覆盖两种浏览器的产物、逐次安装、已有注册保护、在线阻止、写入与注册失败恢复和卸载。磁盘记录校验及平台查询、恢复的既有策略未作为结构重构悄然改变；这些限制不能因增加类型或提取函数就视为已解决。此案例验证了本规则在另一类入口中的应用及其覆盖行为的保持，阅读效果仍待使用反馈。

在后续编排适配反馈中，用户指出固定工具依赖被封装为异步动态导入，且共同分发入口仍嵌入多个完整操作流程。基础原则已要求复杂度有现实依据、共同入口职责收敛；此前审视没有落实到依赖加载依据和逐分支检查，属于执行遗漏，同时暴露了派生规则的触发提示不够具体。本次据明确反馈补充这两个判断入口；不将用户的局部纠正扩大为所有条件分支或动态导入的禁令。相同边界用例在重构前后通过，真实工具与 Schema 的契约检查及类型检查通过，支持所覆盖行为的保持；没有测量启动性能，也未重新真机验收。

在同一适配案例中，用户进一步选择按固定方法名登记函数策略，每项操作负责原有输入校验和业务流程，共同入口保留连接检查与错误转换。这一选择对应独立操作与共同约束的现有结构，说明可以在不引入类或注册框架的前提下收敛分发；不证明此前的简短 switch 必然错误，也不证明其它分支适合相同模式。

后续反馈指出，函数和策略整理后，同一文件仍同时维护契约说明、页面操作、业务读写与 SDK 适配，文件与模块的职责没有得到充分审视。此前主要归为执行遗漏的判断不够完整：稳定原则第三条对边界层次的表达也不够明确。用户认可保留五条原则并补强第三条，明确按职责、共同变化原因和依赖关系审视函数、文件与模块。本次是原则与经验修订，不作为来源代码已完成模块拆分或阅读效果已验证的证据。

### React 页面与组件的职责边界补充

**状态：待验证。最近修订：2026-11-09。对应原则：**让代码易于理解和修改、复杂度与需要相称、用证据建立信心。

**适用范围：**

React 或其他组件化前端项目中，Page、Renderer 或大型 Component 同时承担页面组合、多个业务模块状态、数据转换、副作用和不同业务类型的条件渲染时适用。

尤其关注：

- 页面组件同时承担多个业务模块。
- 一个 Renderer 同时管理不同业务领域。
- 一个组件拥有大量彼此独立的状态。
- 数据过滤、排序、分页和统计直接混入 JSX 所在组件。
- 不同业务模块的弹窗、数据请求和交互逻辑混在同一个文件。
- 已经提取子组件，但文件仍然混合不同变化原因的职责。

**1. 识别组件职责**

审查组件是否同时承担以下职责：

- 页面布局与业务模块组合。
- 多个业务领域的状态管理。
- 数据过滤、排序、分页和统计。
- 外部请求、文件下载等副作用。
- 多种业务类型的条件渲染。
- 多个弹窗与交互流程的协调。

如果这些职责具有不同的变化原因，应进一步判断是否需要拆分。

不能仅因为代码较长就认定需要拆分，也不能因为组件名称是 Renderer 就默认它只负责渲染。

**2. 按语义职责确定边界**

分析以下层次，但不要求每个项目机械建立全部层次：

- Page：路由入口、页面级组合和必要的页面状态协调。
- Renderer：根据工作台或页面配置组合对应业务模块。
- Feature Module：独立业务功能及其状态、交互和数据处理。
- Component：具有明确职责的 UI 展示与交互。
- Hook：具有共同状态和行为的 React 逻辑。
- Selector：纯数据转换、过滤、排序、分页和统计。
- Service：外部数据访问和副作用。
- Store：确实需要跨组件或模块共享的客户端状态。

职责划分应根据项目现有架构和真实变化原因确定，不要求所有业务逻辑都必须进入 Hook、Service 或 Store。

**3. 状态所有权**

- 状态应由最小的共同使用范围持有。
- 单个业务模块使用的搜索、筛选和分页状态，优先归属于该模块。
- 多个模块真正共享的状态，由最近的共同上层协调。
- 不因组件拆分就将所有状态放入全局 Store。
- 状态之间存在复杂转换关系时，评估 reducer 或专用 Hook。
- 不重复维护可以从现有状态直接推导的值。
- 不让多个组件分别维护同一业务事实的不同副本。

**4. 数据逻辑与渲染分离**

- 纯过滤、排序、分页和统计逻辑，优先考虑独立 Selector。
- 数据转换应能够脱离 React 渲染进行测试。
- 外部请求、文件下载等副作用放在具有明确职责的位置。
- 不让页面组件直接承担所有数据处理过程。
- 不要为了提取纯函数而创建大量只有一行转发逻辑的文件。

**5. 业务模块边界**

当不同业务区域具有独立的数据、状态、交互和变化原因时，应考虑独立模块。

例如：

订单、客户、活动趋势分别具有独立的数据和交互时，应比较模块独立维护的收益与跨模块通信成本。

跨模块共享应通过明确的属性、回调、数据契约或项目既有接口完成。

不要让一个业务模块直接依赖另一个模块的内部状态或内部实现。

共享组件只用于具有稳定共同契约的功能。

**6. 文件拆分判断**

拆分文件前先回答：

- 这些代码是否因为同一个业务原因共同变化？
- 它们是否需要共享状态或资源生命周期？
- 是否可以独立理解和修改？
- 拆分后是否需要跨文件追踪更多上下文？
- 是否引入不必要的接口、类型和传递层？
- 新文件是否有明确、稳定的职责？

不要把以下行为视为结构改善的证据：

- 仅将 JSX 移到其他文件。
- 仅将长函数拆成多个小函数。
- 将每个小组件都创建一个文件。
- 为了减少行数而建立大量转发组件。
- 创建只有一个调用方且没有独立语义的抽象层。

**7. 结构验收**

重构前：

1. 绘制组件和模块职责图。
2. 识别状态所有者。
3. 识别数据流和数据转换。
4. 识别外部副作用。
5. 识别跨模块依赖。
6. 确认需要保持的业务行为。

重构后：

1. 检查 Page 是否只承担合理的页面组合。
2. 检查 Renderer 是否主要负责配置驱动的模块组合。
3. 检查业务模块是否可以独立理解和修改。
4. 检查状态是否归属正确。
5. 检查跨模块依赖是否明确。
6. 检查是否产生过度拆分或重复抽象。
7. 分别进行结构复核和行为验证。

测试通过不能证明组件边界合理；文件减少也不能证明可维护性改善。

**8. 来源案例与当前证据**

Shuriva 的 `workspace-renderer.tsx` 是本规则的来源案例。

静态审查发现，该 Renderer 同时承担：

- 不同工作台类型的页面组合。
- 客户选择和联动状态。
- 订单搜索、日期、渠道、排序和分页。
- 订单金额和状态统计。
- CSV 导出。
- 数据源恢复和状态展示。
- 客户资料与客户目录展示。
- 多个弹窗和抽屉的协调。

文件中虽然已经提取了 Metric、ModuleHeading、ModuleFooter、OrderRow、CustomerProfile、CustomerDirectory 等局部组件，但主 Renderer 仍承担大量独立业务职责。

这说明局部组件提取不足以证明文件和业务模块边界合理。

本次仅完成静态代码审查，尚未实施重构，也没有重构前后的行为测试和实际使用反馈。因此本补充规则保持待验证状态。

**9. 反例与适用边界**

以下情况不应机械拆分：

- 单职责的小型页面。
- 简单展示组件。
- 紧密相关的表单状态。
- 必须共同维护的事务或资源生命周期。
- 仅在一个位置使用且没有独立变化原因的小型辅助组件。
- 为表达一个紧密业务流程而需要共同协调的组件。

不设统一的组件行数、文件行数或 JSX 层级阈值。

不要求所有 React 项目采用相同的目录结构。

**10. 修订原因**

本补充来自 Shuriva WorkspaceRenderer 的静态审查。原有 READ-001 已经强调函数、文件和模块三个层次，但针对 React 组件状态所有权、Renderer 职责和业务模块拆分的触发条件不够具体。

本次补充用于指导后续 React 架构审查和重构，不代表已经完成 Shuriva 的代码重构，也不代表其效果已在其他项目得到验证。

### 反例与迁移限制

人工场景复核：单职责的短字段映射、简单事件回调或按浏览器生成少量字段可以内联；职责内聚的小模块，以及需要共同表达事务、状态或资源生命周期的步骤，可以保留在同一函数或文件中。环境选择器若必须避免非当前宿主的模块初始化，动态导入仍有明确用途。

少量直接分支可以保持显式；目标是否存在、输入是否有效等同一操作内的事实判断仍适合条件分支，不按本条强拆成策略。没有统一行数、嵌套层数或拆文件模板，也不禁止 if、switch、for、async、表驱动或对象展开。

迁移到其他技术或项目时，先判断是否同样存在独立职责混杂和阅读负担；不满足条件时不套用，也不为验证通用性扩大任务。

### 修订原因

补充稳定原则缺少的具体触发条件；按用户的跨项目复用要求移出来源仓库链接，改为自包含的案例摘要和迁移条件。安装器反馈补充了操作意图、抽象层次、多阶段表达式，以及行为保持与契约收紧的边界；编排适配反馈进一步补充依赖加载的依据、逐分支职责检查、函数策略表的选择条件及结构验收的证据范围，合并进已有条目。

最新反馈经用户明确认可后补强稳定原则第三条，并将本经验的检查范围从函数与入口扩展到文件和模块；仍保留五条原则，不以文件数或行数作为拆分标准。

本次 React 补充依据 Shuriva 的静态代码审查形成，尚未经过实际重构验证，因此不提升为已验证的通用经验。

## PACK-001：用真实分发形态验证交付

**最近修订：2026-11-06。对应原则：**保证行为可靠、用证据建立信心；验证范围遵循复杂度与需要相称。

**范围与风险：**交付可安装包或本地程序时，消费者的目录布局、依赖、编译产物或启动器与开发环境不同，源码测试和链接安装可能绕过实际限制。打包清单、运行入口、辅助资源或支持路径变化时适用。

### 可执行规则

- 从待交付产物进行实际安装，检查所需运行文件、依赖及辅助资源，并让各角色和客户端都指向同一安装产物。源码运行或链接安装只能证明各自覆盖的形态；不要让部分入口仍偷偷使用源码，从而掩盖包内缺失或加载错误。

- 按实际支持范围选择路径和生命周期用例，例如空格、非 ASCII 字符、更新、重新注册和卸载。若功能依赖用户授权等前置条件，同时核对条件改变前后已有上下文的能力；预授予权限的测试不能证明首次授权路径。跨进程传递数据时核实生产者与消费者的编码；有结构化读取方式时，避免依赖本地化展示文本。卸载检查涉及外部注册时，也核对注册状态，不能只看文件消失。

- 使用隔离安装位置和配置保护日常环境，保留检查依据并清理测试副作用；这不授权安装未批准的新依赖或修改真实用户数据。启动成功后，仍按改动风险验证关键使用链路；将分发故障的修复与无关业务改造分开。

### 来源与验证摘要

一个 Windows 本地桥接包在仓库和链接安装中可运行，实际 npm 安装后，Node.js 24.19.0 拒绝直接移除 node_modules 下 TypeScript 文件的类型；改为分发编译后的 JavaScript 后恢复。

含空格与中文的安装路径又暴露注册表查询编码误读和批处理启动路径乱码；分别通过显式 UTF-8 结构化读取及匹配启动器编码修正。

实际安装包通过全局命令、配置生成、测试版本更新、注册和卸载检查，并经两种浏览器及一个真实 MCP 客户端完成编排、执行、数据读取和重启查询。平台读取另验证缺失值、中文值和非字符串值。具体产物、命令和日志留在来源项目，不作为迁移前提。

后续用户真实启用时又报告权限检查已通过、后台接口却缺失；此前预授予权限的测试未覆盖该状态。新增能力检查与清晰的恢复提示后，单测验证接口缺失与恢复分支；用户重新加载后恢复连接，并由真实客户端检查通过。该证据支持区分授权与接口可用性，以及补查前置状态变化，不证明底层平台的全部绑定机制。

### 反例与限制

不分发安装包的局部任务不必引入 npm 测试；仅修改说明且不影响运行产物时，也不默认重跑完整业务链路。

类型源码是否能直接运行取决于目标运行时和安装形态，不将上述特定版本的限制写成所有语言或包的禁令。

测试更新只证明产物替换与注册流程，不等于不同业务版本兼容；隔离客户端验收也不能证明所有客户端或正式授权界面均已验收。

### 修订原因

真实安装暴露了源码验证无法覆盖的故障，新增该独立场景的判断方法；后续依据真实首次启用反馈补充前置条件变化的验证边界。不把安装器局部修复扩大为所有编码任务的发布流程。
