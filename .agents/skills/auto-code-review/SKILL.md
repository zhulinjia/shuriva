# 自动代码审查（Codex 原生 Review 编排）

## 核心原则

使用 Codex 原生 Review，并将静态审查与行为验证分别记录。按实际能力选择已提供的原生工具、经过能力检查的只读 CLI 或客户端 `/review`；桌面/IDE 会话也可以使用可用的 CLI，不因客户端名称直接要求人工操作。启动前阅读 [执行说明](references/review-execution.md)。

- 安装 Skill 不等于安装执行钩子；依项目约定在交付前实际执行，不伪称必然触发。
- 原生入口无法使用时，完成可做的自查并标记“降级自查”；普通/高风险任务的原生审查仍为未完成，说明具体限制及可用的人工入口，不虚报通过。
- 只读审查请求按用户指定范围及适用的原生入口执行一次，不因交付规则在完成后再追加审查或修复。已经进入原生 reviewer 的进程只检查范围并报告，不再启动嵌套 Review。
- 不安装 Stop Hook、自动提交脚本或递归进程来实现本技能；不修改权限、模型、凭据或全局客户端配置来绕过调用失败。

## 触发时机与范围

- 每个完整代码任务或可独立理解的逻辑变更完成后、最终交付前，执行本技能。
- 大任务可按已完成且可验证的阶段审查。
- 不要在每次保存文件、每次编辑工具调用或中间步骤后启动完整审查。
- 纯讨论、计划、解释且没有改动时不触发。仅调整 Skill 或项目说明时检查文档、引用与适用的结构校验，不为审查规则自身生成递归审查。
- 开始代码任务时记录 Git 起点及已有修改，交付时确认本次文件/差异和必要上下文。提交、任务分支和未提交改动是正常审查来源；先核对实际 diff，不能把任意 base 或 HEAD 当成本次任务起点。
- 审查前排除无关改动。同一文件含混合修改时按差异判断，不只按文件名；不能先全量审查再将无关结果删掉，就称为范围已隔离。
- 尚无首次提交只是临时仓库状态。没有可靠差异时明示范围限制，以指定文件和需求作有限自查或经明确指定作初始审查；不得声称完成本次增量 Review。之后直接使用正常 Git 流程，不创建长期快照系统，不为审查擅自提交或更改工作区。

## 风险分级与动作

### 低风险：轻量自查
适用：纯注释/说明文档、确认语义不变的格式化、非功能文案、不影响交互和无障碍的局部样式。
- 检查本次 diff，确认无意外行为变化。
- 必要时运行快速检查、Lint 或界面预览。
- 默认不调用原生 Review，除非用户明确要求或检查发现风险升级。
- 简短报告。

### 普通风险：原生 Review
适用：功能开发、业务规则、API 调用、状态管理、持久化、后台任务、普通 Bug 修复、异常处理和重试。
- 任务完成并确定范围后，按执行说明选择当前可用的原生入口。
- 原生审查默认只报告问题，不会自动修复。
- 核实发现并运行与变更相适应的检查；已经完成且仍有效的测试不为凑次数重复运行。

### 高风险：原生 Review + 专项验证
适用：认证/授权/租户隔离/隐私/密钥；支付/计费/点数/额度；删除/迁移/备份；并发/竞态/幂等/重试/事务；公共 API/Schema 兼容；部署/CI 权限/基础设施。
- 调用原生 Review，检查完整受影响调用链。
- 增加针对风险的测试或验证，例如权限矩阵、重复请求、回滚、迁移安全、并发场景。
- 额外的专业视角审查按实际风险选择；它与已确认缺陷修复后的核验分别处理。
- 检查失败路径和恢复行为；构建成功或类型检查通过不足以证明安全。

## 风险判断

按影响、影响范围和可恢复性判断，不按代码行数判断。需要进一步判断时阅读 [风险分级标准](references/风险分级标准.md)。
小改动也可能高风险；大量机械格式化若能证明语义等价，也可能低风险。
无法排除严重影响时，按较高等级处理并说明不确定性。

## 审查结果处理

- 逐项核实原生审查报告中的问题，区分真实缺陷、待验证疑点和建议。
- 每个确认问题记录严重程度、文件/行号、触发条件、影响和证据。
- 当前任务已授权修复时，可以修复本次范围内确认的缺陷。
- 不得因可选建议擅自扩大需求、重构无关代码或升级依赖。
- 用户明确要求“只审查”时必须只读。
- 修复后只复查修复位置和受影响调用路径，并重跑相关测试。
- 已确认的高风险修复需要针对性原生复查；不因“默认一轮”跳过。默认先做一轮原生审查，不无理由重复全仓扫描；重复问题或能力限制导致无法完成时保留未完成状态和证据，不无限重试。

## 项目规则与执行边界

- 读取适用的 `AGENTS.md`、需求/阶段设计及用户当前约束；原生审查不自动获得本聊天的全部背景。确保必要约束可通过受支持的审查上下文或项目规则传入。
- 核查模块职责与依赖、当前调用方、权限/数据边界及失败恢复；本项目的 SQL、确认、Connector 绑定、未知结果、凭据/日志和模型发送规则以项目文件为准，不在技能中复制整套业务设计。
- 尊重尚未上线、无需假设旧版本兼容及已确认的 G4 排除范围；不把用户已排除的实机测试重新列为当前阻断项。
- reviewer 只读，不执行迁移、数据库修复、清理或服务重启。相关测试由主任务使用已授权的隔离 fixture 执行，不从原库或默认连接回退；不读取密钥文件、真实凭据库或运行目录来扩大审查上下文。
- Claude Code 按相同项目规则和此文件提供范围、验证结果与约束，通过实际可用的 Codex 原生入口审查。不能调用时如实降级，不把 Claude 自查标为 Codex 原生 Review；不假定其他客户端会自动发现此目录。

## 完成条件与证据

- **通过（当前范围）：** 所需原生审查已完成，适用检查通过，无未解决的已确认阻断问题。仅说明当前范围，不能称为“全部安全”。
- **不通过：** 存在未解决的已确认 P0/P1、关键安全不变量失效或相关必要检查失败。疑点先核实，不把可选建议当作缺陷。
- **未完成：** 必需审查尚未执行、超时/中断、缺少结果或关键范围/验证不完整；降级自查仍需保留该说明。
- 记录审查入口、目标/文件范围、Git 基准或明确的无基准状态、完成状态和主要结果。以提交标识或任务差异清单绑定被审查版本；后续实质修改必须核验受影响部分，不能复用旧版本结论。无需为此建立新快照或持久服务。

## 最终报告

普通/高风险交付明确说明以下内容；低风险文档自查简短说明实际检查和限制即可：
1. 是否实际执行了 Codex 原生 Review。
2. 使用的客户端入口和审查范围。
3. 原生审查发现及核实结果。
4. 实际运行的测试及结果。
5. 修复后复查范围。
6. 未执行的检查和剩余风险。

绝不把自查说成原生 Review；绝不声称运行了未执行的测试；不得无证据地说“全部安全”。
