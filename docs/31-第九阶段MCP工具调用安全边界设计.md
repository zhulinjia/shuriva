# 第九阶段：MCP 外部工具调用安全边界修订方案

状态（2026-11-03）：已按用户授权实施订阅、完整快照和本地移交控制，恢复符合下述条件的发现、工具批准及单次调用；原先无条件关闭这些能力的临时门禁已由当前校验替代。本轮专项验证及具体局限见 [G4 修订记录](29-第九阶段G4实施与审核记录.md)，最终独立 Agent 和 Codex 原生复审由主任务统一执行，本记录不提前宣称其通过。第九阶段整体进度见 [G5 联调与验收记录](30-第九阶段G5联调与验收记录.md)。历史清单和旧页面状态不构成当前可调用事实。

## 1. 问题和信任边界

平台批准的是某次经验证的工具描述、输入输出结构和连接范围；外部工具及其结果仍是不可信输入。批准不意味着服务进程只能执行所描述的行为，也不使工具名称或提示成为事实。管理员必须信任所选服务及其运营方，尤其要理解本机 stdio 程序拥有该操作系统用户的实际权限。

当前安装的 MCP SDK 公开 `listen()` 和 `McpSubscription`：前者在服务端确认订阅后返回，后者提供被接受的筛选范围和断开状态；订阅中断不会自动恢复。SDK 中当前协议的工具列表变化筛选项为 `toolsListChanged`。标准 `tools/call` 的业务参数包含工具名称和参数，未发现要求服务端按客户端指定的完整清单哈希原子执行的标准条件。实际实现必须基于项目锁定的 SDK 公开接口和协议契约验证，不依赖 SDK 内部模块。

**本方案只能保证本机已经处理到的事件顺序，不能保证服务端实际执行时仍使用已审查的工具版本。** 远端可能先改变实现、随后才发送通知，通知也可能仍在网络途中；恶意或故障服务可能不按承诺发送通知。服务进程是否遵守协议也无法仅凭订阅、哈希或提示证明。对要求远端执行与批准版本原子一致的场景，需另行设计并验证双方支持的条件执行或可信受控宿主；标准调用无法单方面提供这一保证。

本轮按已确认的阶段授权实施以下取舍：在管理员明确选择并信任服务的前提下，平台以完整清单核验和**本机可观察的移交顺序**提供控制，并在界面明确上述限制。设计授权不代替实际实现、测试和复审。

## 2. 订阅和完整清单

1. 创建连接后，在任何用于批准或派发的发现之前，使用锁定 SDK 的公开订阅接口建立工具变更订阅，等待确认；核验服务端实际接受的筛选范围包含 `toolsListChanged`。订阅、确认、连接和等待都必须有界，不能静默退化为未订阅模式。
2. 没有相应能力、订阅确认未包含工具变更、确认超时、订阅异常结束或连接中断时，该连接的工具调用保持不可用。不能将服务未声明通知能力推断成工具永远不变。是否支持其他具备可验证不变性保证的受控服务，需要独立方案和证据。
3. 为连接维护一个不可复用的本地订阅代次。订阅确认后开始完整分页发现；严格关联请求和响应，限制体积、深度、节点、工具数量和页数，拒绝重名、缺页、游标循环、非法结构及未知结果。完整原始清单中的所有工具和未识别字段均参与版本承诺；不支持的工具只可显示为不可批准、不可调用。
4. 从订阅建立、发现、审批到派发前复核，均以同一有效代次为前提。收到工具清单变化通知或订阅失联后，立即使本地代次失效；不得继续发布正在发现的快照或继续以该代次派发。应重新建立有效订阅、完整发现并比较当前清单与用户批准，按现有规则决定是否需要重新批准；不能因重新发现而静默扩权。
5. 已保存的快照或批准保留为历史事实，不自动修改已有数据。当前登录会话必须持有同连接版本的存活订阅和刚完成的完整快照；管理响应以服务端 `toolsVerified` 明确表达这一事实。重启、断开或订阅失效后，该字段为 false，必须重新发现；不能从 `connected`、已有 hash 或前端缓存推断已核验，不凭空假定存在已发布旧版本。

## 3. 本机移交与结果状态

本方案把**将一次 `tools/call` 请求交给本机传输拥有者**视为不可逆移交点，不把套接字写入成功、stdio 宿主回执或协议返回当作远端已执行的证明：

- **HTTP：** 移交点不得晚于任何可能将调用请求交给 Node、操作系统或网络队列的操作；不能把 `request.end()` 完成、`finish` 事件或服务端响应解释成首次移交。具体位置须根据实际传输实现和故障测试确定，若不能证明尚未移交，应保守记为可能已移交。
- **stdio：** 不得晚于将调用帧交给宿主 IPC 或其他可能继续转发的队列；宿主之后写目标进程、持有发送许可或返回回执，都不能证明先前未移交。不得把删除许可文件、杀死进程或取消 Promise 当作对方未执行的证据。

派发前必须先持有实际管理员会话、工作区、连接及凭据代次的有效授权，完成动作审计，再由同一串行化协调器核验订阅存活、本地代次、完整快照、已批准工具、参数承诺和取消状态。持久记录和其他可能等待的工作必须在最后一次核验之前完成；最后核验到移交之间不得插入可让其他任务改变授权状态而未重新检查的异步空隙。物理授权租约及其终止处理仍适用。

协调器只能按**它已经观察到的事件**排序：若在移交前观察到工具变化、订阅失联、权限失效或用户取消，必须阻止该次交出调用，并在能证明未移交时记录确定的未发送状态。通知可能已产生但本机尚未收到，不能据此断言远端没有变化。

移交可能发生后，如随后出现通知、失联、超时、撤销、进程退出或无法确定结果的故障，应尽力取消，但将执行结果记为 `outcome_unknown`，保留原编号，不自动重放；不能声称取消阻止了外部副作用。只有在授权有效、协议响应完整且按现有边界校验后才能展示实际收到的结果；结果只代表服务的响应，不代表平台已独立核验业务副作用。若在结果发布前发生使结果可信范围不明的变更，按未知处理并要求管理员核对。

持久化记录需要在可能移交之前留下足够的无敏感内容事实，以便进程中断后不把可能已发送误记为未发送。由于持久记录和物理发送不能组成跨系统原子事务，若进程在两者之间崩溃且无法证明未交出，恢复必须保守记为未知。参数、凭据和结果仍不得写入普通审计或诊断日志。

## 4. 管理界面与操作

- 服务不可调用时，工具列表保留查看能力，清楚显示安全验证未完成；服务端也必须拒绝准备、确认及所有直接派发入口，不能只禁用按钮。
- 建立有效订阅并完成全量发现后，界面展示连接目标、工具名称和已批准版本；不支持、清单变化、订阅失联、审批过期分别有明确状态。变更后需要重新核验，新增工具默认不批准。
- 单次调用前继续展示实际参数和外发范围，要求明确确认；界面说明该调用会交给管理员信任的外部服务，平台无法保证服务端实际执行实现与已展示版本原子一致，也无法保证取消会撤销副作用。
- 未发送、等待外部服务、已收到结果、结果未知分别展示；未知状态保留原编号与人工核对入口，不提供自动重试或将未知描述为失败。订阅失联时展示不可调用，不靠旧页面或旧批准继续执行。
- 所有阻断准入的未核对未知调用必须能从历史入口逐项触达，包括已释放 slot 后恢复为未知的记录。当前历史窗口有界为 50 条，优先未核对未知，再按时间和编号排序；核对后推进窗口，不让更新的已核对记录永久隐藏更早的阻断项。

## 5. 实施与隔离验证门槛

继续只使用新建的独立测试实例、虚构数据和明确拥有的测试进程，不连接、迁移、修复或重置用户原数据库。实际实现前先核验现成 SDK/传输能力和所需扩展，再按下列阶段分别留存证据：

1. **协议能力验证：** 锁定 SDK 和协议版本，验证订阅确认、`honoredFilter`、拒绝或缺失能力、确认超时、订阅结束、连接断开、取消以及重连后新代次。分别覆盖 HTTP 和本机 stdio；不把某一服务的结果外推至其他服务。
2. **完整发现与批准：** 多页发现期间注入变更、重复及错误响应、ID 类型混淆、超限和未知 schema；确认无法提交混合版本，已支持和不支持工具均参与原始清单版本承诺，变更不静默扩权。
3. **可观察移交竞争：** 在审计等待、最终核验前后、HTTP 队列与 stdio 宿主 IPC 前后精确注入通知、断连、撤销和取消。证明本机已观察到的变更在移交前可阻止请求；对无法证明未移交的路径一律验证未知且不重放。真实网络和进程故障测试不得将“尽力取消”解释成外部副作用一定不存在。
4. **恢复与用户体验：** 测试崩溃发生在持久记录与移交之间、移交后响应丢失、结果到达前订阅失联，以及重连后审批重新核验。用真实浏览器验证状态、目标及披露提示，确保管理员能识别未知结果和执行范围。
5. **风险复审：** 按项目代码审核 skill 对最终实现和受影响调用链运行 Codex 原生审查；核实问题、修复、重跑相关测试，对高风险修复定向原生复审。分别记录已验证的本地组合和未验证的平台/服务范围，不把模拟服务、订阅成功或测试通过表述为服务端原子版本保证。

用户已决定不进行真实断电、实机休眠/恢复及物理磁盘故障实测；这些项目不作为当前关卡阻断，也不记为已验证。安全的网络、进程与存储错误测试仍按既定要求执行。

## 6. 当前实现映射（2026-11-03）

- `driver.ts` 通过公开 SDK 订阅接口取得确认；订阅使用连接终止信号，短发现操作结束不会终止已确认的订阅。订阅结束没有自动恢复、重放或未订阅退化路径。
- `discovery.ts` 和 `transport.ts` 校验完整分页及准确响应标识；不可复用的本地代次在通知/失联时失效。`service.ts`、`calls.ts` 在发现保存回调中再次核验完整 hash 和本地代次；在工具批准、调用准备、确认和实际消息移交前分别检查适用事实。
- 实际调用消息先生成受限的不可变规范化值，一次性许可检查其中真实的工具名和参数承诺。HTTP 的同步最终检查位于交给 Node `request.end(body)` 之前；stdio 位于交给已拥有宿主的发送操作之前，不能把宿主回执当作首次移交。
- 已确认订阅、完整快照及同会话/版本关系共同决定响应中的 `toolsVerified`。`lifecycle` 单独报告连接、关闭中、清理未知和已断开；关闭中及未知时不返回虚假的 `connected:false`。这些展示事实不替代每次实际派发的数据库授权租约。
- `close()` 拥有尚未完成的建立过程及全部资源清理；并发关闭等待同一个最终结果。清理不确定保留名额及固定错误，不推测进程已退出；所有传输及嵌套发送的错误先脱敏再保留或返回。
- 原结果保留准确订阅代次及失效信号，缓存后观察到变化也立即停止披露；读取和实际 HTTP 写入再查原证据、授权租约及生命周期。数据库内部以 `result_retained` 记录尚未完成平台响应发送或正常到期的结果，不把该中间阶段作为公开终态；重启恢复为未知。旧 slot 为空也不能绕过未核对未知结果的准入限制。已经正常完成的平台响应发送不证明客户端收到，后续事件会使缓存失效，但不改写此前已交出结果的事实。
- 创建驱动及所有 readiness 校验共用 `closing`/`cleanup_unknown` 硬门禁；关闭标志先于实际清理回调登记。摘要和 UI 不承担这一拒绝责任，直接 API 也不能在关闭未确认时创建替代执行主体。

具体已运行命令、修复中的失败批次、实际结果、尚未验证组合以及原生复审状态见第 29 号记录末节。远端原子版本执行仍不属于本实现保证。
