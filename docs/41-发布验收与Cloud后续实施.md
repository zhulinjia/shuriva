## Cloud 数据与授权的实现边界

- **结构与语义规划。** 复用 Connector 的签名 `model_schema` 和 `model_authorize` 任务，以当前绑定和本机策略核验结构。原始结构短暂保留，发送前用当前授权范围重新投影，预览只展示将发送的问题、结构、明确可发送的语义和目的地。源、绑定、结构、语义或模型配置变化使确认失效。模型返回结构化建议，由服务端验证，执行仍走独立的只读查询流程。
- **受控写入。** 用户已确认 Owner / Admin 发起，由同组织另一名 Owner / Admin 确认。按账号标识区分两人，同账号不同会话不能自批。两人的身份、当前角色、工作区和来源绑定在签发提交许可前重验。双身份事务先按稳定顺序核验会话，再锁组织及操作记录，避免持有组织锁时反向等待另一方会话。复用 Connector 的 Go 执行器、策略校验、本机日志和回执。把依赖 Community `ownerId` 的签名作用域扩展为明确的 Cloud 租户、两名参与者、工作区、数据源和 Connector，按版本发布公共合同。隔离验收覆盖跨租户、同账号自批、并发确认、许可前撤权、行或结构变化、提交回执丢失，以及重启后只查证原执行。预览可见范围及解除冻结规则仍需纳入权限表，正式写入入口继续关闭。
- **MCP OAuth。** 用户已确认 Owner / Admin 手工登记客户端并批准授权，按具体工作区和数据源授予只读工具。优先复用现有 MCP SDK 及 Better Auth 的 MCP 插件。按实际配置绑定 issuer、resource、redirect 和登记的客户端，使用授权码和 PKCE。浏览器会话用于登录和审批，工具调用使用资源专用令牌。Cloud 自建租户授权记录，每次调用和读取结果都重验授权、绑定及成员资格。隔离验收覆盖错误 audience、授权码重放、跨租户访问和撤销。
